# Contributing Packages to Rustget

This document describes how package entries are structured and how to add a new one.

## File layout

Packages are grouped by category into JSON files under `data/`:

```
data/
  browsers.json
  media.json
  dev-tools.json
  archivers.json
```

Each category file looks like:

```json
{
  "category": "browsers",
  "index": ["zen", "helium"],
  "packages": [
    { ... full package object ... }
  ]
}
```

- `index` is a lightweight list of package names in this category, used for fast lookups without scanning full package objects.
- `packages` holds the full metadata object for each entry.

## Package schema

| Field         | Type            | Required | Notes |
|---------------|-----------------|----------|-------|
| `name`        | string          | yes      | lowercase, no spaces |
| `version`     | string          | yes      | current stable release version |
| `description` | string          | yes      | see style rules below |
| `category`    | string          | yes      | must match the file it lives in |
| `homepage`    | string \| null  | yes      | official website, `null` if unknown |
| `downloadUrl` | string          | yes      | **must** be a direct, versioned release asset link (see policy below) |
| `sha256`      | string          | yes      | **must be entered manually** — see policy below |

## `downloadUrl` policy — direct links only, no "smart" download pages

Do **not** use a site's auto-detecting `/download` page (the kind that detects your OS/arch via JavaScript and redirects or triggers a script-based download). These break for two reasons:

1. **Not fetchable by a plain HTTP client.** Rustget downloads files with `reqwest`, which has no JS engine. If the "download" is actually triggered by client-side JS, `reqwest` will just receive the HTML page itself, not the binary.
2. **Not stable.** The same URL can silently start serving a different file after a new release ships, which breaks hash verification for anyone installing after that point.

Instead, use a **direct, versioned release asset URL** — e.g. a GitHub Releases download link:

```
https://github.com/{owner}/{repo}/releases/download/{tag}/{filename}
```

To find one: open the project's Releases page, locate the exact asset for the target platform, right-click it, and copy the link address. If a site only offers a smart download page, check its network requests (DevTools → Network tab) while triggering the download to find the underlying direct file URL.

## `sha256` policy — always manual, never generated by a tool or AI

The hash must come from **the publisher's own published checksum** (their release notes, a `SHA256SUMS` file, etc.), copied in by a human. It is never:

- guessed or fabricated by an AI,
- computed automatically by Rustget from its own download of the file.

Why: a checksum only protects against tampering if it comes from a source independent of the download itself. If Rustget downloaded a file and hashed it, the hash would only ever confirm the download matched itself — not that the file is legitimate. A human manually copying the publisher's own hash is what makes the check meaningful.

## Description style rules

- One factual sentence, under 15 words.
- Name 2–3 concrete, specific features or technical facts that distinguish this app from others in its category (e.g. "vertical tabs", "no telemetry", "built on Chromium", "workspaces") — not vague trait words like "modern," "clean," "powerful," or "beautifully designed."
- Do not restate the category (don't say "a web browser for browsing websites").
- No subjective claims, no first-person language ("we care about..."), no marketing tone.
- No trailing punctuation.

**Good:**
- `Firefox-based browser with workspaces, split views, and vertical tabs`
- `Chromium-based browser without telemetry or mandatory account integration`
- `Media player supporting most audio and video formats via ffmpeg`

**Bad (too vague / marketing):**
- `Beautifully designed browser focused on your privacy`
- `Powerful and feature-packed media player`
- `A modern browser experience`

## AI prompt for drafting a new entry

Use this with any AI assistant to draft the text fields for a new package. It intentionally excludes `sha256`, since that field must always be added manually afterward.

```
You are writing a metadata entry for an app in a package manager registry (similar to apt, homebrew, or winget).

App name: {APP_NAME}

Write a JSON object with exactly these fields, in this exact order:
- "name": lowercase, no spaces
- "version": always output this as an empty string ""
- "description": one factual sentence, under 15 words
- "homepage": the app's official website URL, if known — otherwise ""
- "downloadUrl": always output this as an empty string ""
- "sha256": always output this as an empty string ""

Only "name" and "description" should actually be filled in with real content. "version" and "downloadUrl" are always left as "" — they get verified and filled in by hand, since a wrong version/link is easy to introduce and easy to overlook if the AI guesses. "sha256" is always left as "" too — it must come from the publisher's own published checksum, entered manually, never guessed, fabricated, or self-computed. "homepage" can be filled in if you're confident, but leave it "" if unsure.

Rules for description:
- Name 2-3 concrete, specific features or technical facts that distinguish this app from others in its category (e.g. "vertical tabs", "no telemetry", "built on Chromium", "workspaces") — not vague trait words like "modern," "clean," "powerful," or "beautifully designed"
- Do not restate the category (don't say "a web browser for browsing")
- No subjective claims, no first-person language ("we care about..."), no marketing tone
- No adjectives that can't be verified as fact
- No trailing punctuation

Good examples:
- "Firefox-based browser with workspaces, split views, and vertical tabs"
- "Chromium-based browser without telemetry or mandatory account integration"
- "Media player supporting most audio and video formats via ffmpeg"

Bad examples (too vague/marketing):
- "Beautifully designed browser focused on your privacy"
- "Powerful and feature-packed media player"
- "A modern browser experience"

Output ONLY the JSON object, nothing else — no explanation, no markdown fences.

Example output for "helium":
{
  "name": "helium",
  "version": "",
  "description": "Chromium-based browser without telemetry or mandatory account integration",
  "homepage": "https://helium.computer",
  "downloadUrl": "",
  "sha256": ""
}
```

## Workflow checklist for adding a package

1. Run the AI prompt above with the app name to draft `name`, `version`, `description`, `category`, `homepage`, `downloadUrl`.
2. Verify `downloadUrl` is a direct, versioned release asset link — not a smart download page.
3. Find the publisher's official checksum for that exact file and copy it into `sha256` by hand.
4. Add the entry to the correct `packages/` array in the matching category file, and add its `name` to that file's `index` array.
5. Double check `version` matches what's actually in the `downloadUrl` (tag/filename).
