# Contributing Packages to Rustget

This document describes how package entries are structured and how to add a new one.

## File layout

Packages are grouped by category into JSON files under `data/`:

```
data/
  browsers.json
  media.json
  dev-tools.json
  archivers.json
```

Each category file looks like:

```json
{
  "category": "browsers",
  "index": ["zen", "helium"],
  "packages": [
    { ... full package object ... }
  ]
}
```

- `index` — a lightweight list of package names in this category.
  Used for fast lookups without scanning full package objects.
- `packages` — holds the full metadata object for each entry.

## Package schema

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | yes | lowercase, no spaces |
| `version` | string | yes | current stable release version |
| `description` | string | yes | see style rules below |
| `category` | string | yes | must match the file it lives in |
| `homepage` | string \| null | yes | official website, `null` if unknown |
| `downloadUrl` | string | yes | must be a direct, versioned release asset link |
| `sha256` | string | yes | must be entered manually |

## `downloadUrl` policy

**Direct links only. No "smart" download pages.**

Don't use a site's auto-detecting `/download` page — the kind that detects your OS/arch via JavaScript and redirects or triggers a script-based download.

Two reasons these break:

1. **Not fetchable by a plain HTTP client.**
   Rustget downloads files with `reqwest`, which has no JS engine.
   If the "download" is triggered by client-side JS, `reqwest` just receives the HTML page — not the binary.

2. **Not stable.**
   The same URL can silently start serving a different file after a new release ships.
   That breaks hash verification for anyone installing after that point.

**Instead, use a direct, versioned release asset URL.**

Example — a GitHub Releases link:

```
https://github.com/{owner}/{repo}/releases/download/{tag}/{filename}
```

How to find one:

- Open the project's Releases page.
- Locate the exact asset for the target platform.
- Right-click it, copy the link address.

If a site only offers a smart download page:

- Open DevTools → Network tab.
- Trigger the download.
- Find the underlying direct file URL in the requests.

## `sha256` policy

There's a strict order of preference here. Work top to bottom — only drop to the next tier if the one above genuinely isn't available.

### Tier 1 — Publisher-provided checksum (preferred)

The hash should come from the publisher's own published checksum:

- their release notes
- a `SHA256SUMS` file
- a signed manifest

Copied in by a human. It is never:

- guessed or fabricated by an AI
- computed automatically by Rustget from its own download, when a publisher checksum exists

**Why this matters:**

A checksum only protects against tampering if it comes from a source independent of the download itself.

If Rustget downloaded a file and hashed it, that hash only confirms the download matched itself — not that the file is legitimate.

A human manually copying the publisher's own hash is what makes the check meaningful.

### Tier 2 — Other independent sources

If the publisher publishes no checksum anywhere — no release notes, no `SHA256SUMS`, no signed manifest — don't jump straight to computing one yourself.

Check these first, in order:

1. **Third-party package manifests.**
   The binary is often already packaged elsewhere with a hash from a separate review process.
   Check a winget manifest or Chocolatey package for the same release/version.
   Use that hash only if you can confirm it matches your exact file/version.

2. **Multiple independent downloads.**
   Download the file from two different vantage points — different network/region, or ask someone else to download it separately.
   Confirm the hashes match each other before trusting either one.

3. **Reproducible build.**
   If the project supports reproducible builds, build from source.
   Confirm the hash matches the published binary.

### Tier 3 — Corroborated self-computed hash

If none of Tier 2 is available, don't just compute a hash and call it done. Corroborate it first:

1. Compute the hash yourself: `rustget sha256 installer.exe`
2. Find a second, independently-computed hash for the *exact same file/version*.
   Example: a Chocolatey or winget package's checksum — even if that manifest's hash was itself auto-generated by a bot from its own download.
3. Confirm the two match.

**What this does and doesn't prove:**

- ✅ Rules out tampering or corruption specific to one download path — a bad CDN edge node, a MITM on your network, a corrupted local copy.
- ❌ Does *not* rule out the file being compromised at the source. If the publisher's own release was tampered with before either download happened, both computations would match — and both would be wrong.

This is a real but limited improvement over a single self-computed hash. It is not equivalent to a genuine publisher-issued checksum.

**Note on bot-generated manifests:**

Many third-party package manifests — Chocolatey AU-maintained packages especially — compute their checksum by downloading the file and hashing it automatically. Same method as `rustget sha256`.

Check the package's update script (e.g. an `update.ps1` using `update -ChecksumFor all`) if you want to know whether a manifest's hash is publisher-sourced or bot-computed.

Either kind is still useful for corroboration. Neither is a substitute for a real publisher checksum.

Note in the PR description which second source was used to corroborate.

### Tier 4 — Last resort: bare `rustget sha256`

Only use this if nothing above is available — including no second source to corroborate against.

```
rustget sha256 installer.exe
```

- Enter the resulting hash in **lowercase**.
- This is the weakest option. It confirms the file hasn't changed *since the entry was added* — but doesn't independently verify the file was legitimate at the time of download, since Rustget is both the downloader and the hasher.
- Note in the PR description that no independent checksum or corroborating source could be found, and that this fallback was used. That way reviewers know to give the entry extra scrutiny.

## Description style rules

- One factual sentence, under 15 words.
- Name 2–3 concrete, specific features or technical facts that distinguish this app from others in its category.
  Examples: "vertical tabs", "no telemetry", "built on Chromium", "workspaces".
  Not vague trait words like "modern," "clean," "powerful," or "beautifully designed."
- Don't restate the category. Don't say "a web browser for browsing websites."
- No subjective claims.
- No first-person language ("we care about...").
- No marketing tone.
- No trailing punctuation.

**Good:**

- `Firefox-based browser with workspaces, split views, and vertical tabs`
- `Chromium-based browser without telemetry or mandatory account integration`
- `Media player supporting most audio and video formats via ffmpeg`

**Bad (too vague / marketing):**

- `Beautifully designed browser focused on your privacy`
- `Powerful and feature-packed media player`
- `A modern browser experience`

## AI prompt for drafting a new entry

Use this with any AI assistant to draft the text fields for a new package.

It intentionally excludes `sha256` — that field must always be added manually afterward, following the checksum policy above:

1. Publisher checksum
2. Other independent sources
3. Corroborated self-computed hash
4. Bare `rustget sha256` — absolute last resort

```
You are writing a metadata entry for an app in a package manager registry (similar to winget).

App name: {APP_NAME}

Write a JSON object with exactly these fields, in this exact order:
- "name": lowercase, no spaces
- "version": always output this as an empty string ""
- "description": one factual sentence, under 15 words
- "homepage": the app's official website URL, if known — otherwise ""
- "downloadUrl": always output this as an empty string ""
- "sha256": always output this as an empty string ""

Only "name" and "description" should actually be filled in with real content.

"version" and "downloadUrl" are always left as "". They get verified and filled in by hand — a wrong version/link is easy to introduce and easy to overlook if the AI guesses.

"sha256" is always left as "" too. It must come from the publisher's own published checksum, entered manually.

If the publisher provides none, other independent sources are checked next: third-party package manifests, independent re-downloads, reproducible builds.

If none of those exist, compute it with `rustget sha256 <file>` and corroborate it against a second independently-computed hash before trusting it.

A bare, uncorroborated `rustget sha256` result is only used as an absolute last resort.

Always entered in lowercase. Never guessed or fabricated.

"homepage" can be filled in if you're confident, but leave it "" if unsure.

Rules for description:
- Name 2-3 concrete, specific features or technical facts that distinguish this app from others in its category (e.g. "vertical tabs", "no telemetry", "built on Chromium", "workspaces") — not vague trait words like "modern," "clean," "powerful," or "beautifully designed"
- Do not restate the category (don't say "a web browser for browsing")
- No subjective claims, no first-person language ("we care about..."), no marketing tone
- No adjectives that can't be verified as fact
- No trailing punctuation

Good examples:
- "Firefox-based browser with workspaces, split views, and vertical tabs"
- "Chromium-based browser without telemetry or mandatory account integration"
- "Media player supporting most audio and video formats via ffmpeg"

Bad examples (too vague/marketing):
- "Beautifully designed browser focused on your privacy"
- "Powerful and feature-packed media player"
- "A modern browser experience"

Output ONLY the JSON object, nothing else — no explanation, no markdown fences.

Example output for "helium":
{
  "name": "helium",
  "version": "",
  "description": "Chromium-based browser without telemetry or mandatory account integration",
  "homepage": "https://helium.computer",
  "downloadUrl": "",
  "sha256": ""
}
```

## Workflow checklist for adding a package

1. Run the AI prompt above with the app name.
   Draft `name`, `version`, `description`, `category`, `homepage`, `downloadUrl`.

2. Verify `downloadUrl` is a direct, versioned release asset link — not a smart download page.

3. Get the `sha256`, in order:
   - Publisher's official checksum for that exact file → copy by hand.
   - If none exists → check third-party manifests, independent re-downloads, or a reproducible build.
   - If none of those exist → compute with `rustget sha256 installer.exe`, then corroborate against a second independently-computed hash if you can find one.
   - If you truly can't corroborate → use the bare `rustget sha256` result as an absolute last resort.
   - Enter the result in lowercase.
   - Note in the PR description which tier was used.

4. Add the entry to the correct `packages/` array in the matching category file.
   Add its `name` to that file's `index` array too.

5. Double check `version` matches what's actually in the `downloadUrl` (tag/filename).
